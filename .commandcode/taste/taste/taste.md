# Taste
- Prefers frequent atomic git commits, one after every checkpoint/milestone in the workflow, rather than batching changes into fewer, larger commits. Confidence: 0.9
- Prefers frontend-only, no-server variants of an app: when asked for a "lite" version, keep all visual/UI features intact but strip backend, database records, checks, and scorings (client-side only). Confidence: 0.9
- Prefers eliminating backend/network dependencies from the app in favor of fully client-side execution (e.g., swapping a remote runner API for an in-browser WASM runner from the same author's repo) so compile/test works completely offline with zero network calls. Confidence: 0.7
- Prefers static/embedded data over runtime fetching of source files: exercise/content data should be generated into JSON at build time (codegen script from source of truth) so the app has zero runtime backend dependency. Confidence: 0.7
- Prefers splitting generated data into a lightweight index plus per-item files loaded on demand (dynamic import) so the initial page load stays small, mirroring lazy per-item fetch behavior of the original app. Confidence: 0.6
- Prefers persisting user progress in localStorage (per-user keys) when no backend exists, including merging local progress on login identity changes. Confidence: 0.6
- When adding a stripped-down sibling app, prefers reusing the existing stack/tooling (same bundler, same framework versions) for parity rather than introducing new tooling. Confidence: 0.5
- Prefers frontend apps to be deployable to GitHub Pages via the `gh-pages` package: sets a `homepage` base URL matching the served site URL, adds `predeploy`/`deploy` scripts that publish the build to the root of the `gh-pages` branch on `origin` (e.g., `gh-pages -d build --remote origin` → https://shramee.github.io/starklings), and a `.nojekyll` marker so JS chunks deploy without Jekyll interference. Confidence: 0.8
- When deploying under a gh-pages subpath, all runtime asset references (logo, wallet icons, modal images) must be `process.env.PUBLIC_URL`-prefixed or relative so they resolve correctly under the subpath — a broken logo/assets in the deployed app is treated as a bug to fix. Confidence: 0.7
- Wants a PR summary generated for the branch's work, grounded in actual git state (branch name, commit log vs base branch, `git diff --stat`/`--name-status`) rather than written from memory — the summary should cover what changed, files touched, verification, and how to run/deploy. Confidence: 0.4
- Prefers keeping third-party code as an npm dependency rather than vendoring it into the repo — questioned "why didn't you use the npm package?" when a dependency was vendored, even when the published package couldn't be bundled by the toolchain; prefers build-tooling workarounds (e.g., patch-package) that keep the npm dep and keep large artifacts out of the repo; when a new version of the rejected package is released, asks to retry the npm-package route (e.g., "try again with new version 0.2.0") rather than accepting the vendored fallback. Confidence: 0.9
- Wants tests whenever a dependency or integration is swapped/changed — after migrating from vendored code to an npm dependency (e.g., a WASM runner), asks for tests to verify the new integration works properly, and expects the tests to match the dependency's own test patterns/API. Confidence: 0.5
- When learning about a third-party dependency, prefers consulting the official published docs (e.g., the package's npm page/README) over digging into the package's source code on GitHub or the npm registry — e.g., "just read the docs on cairo-runner npm page". Confidence: 0.6
